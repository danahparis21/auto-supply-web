1   Introduction

The Test Plan is designed to prescribe the scope, approach, resources, and schedule of all testing activities of the project AutoSupply POS and Inventory Management System.

The plan identifies the items to be tested, the features to be tested, the types of testing to be performed, the personnel responsible for testing, the resources and schedule required to complete testing, and the risks associated with the plan.

1.1 Scope

1.1.1 In Scope

All the features of the AutoSupply POS and Inventory Management System which were defined in the software requirement specification are needed to be tested:

1.1.2 Out of Scope

These features are not to be tested because they are not included in the software requirement specification:

  • Third-party payment gateway integration (system records cash payment/change only)
  • Multi-branch/multi-store synchronization
  • Native mobile application version
  • Hardware interfaces (barcode scanners, receipt printers) unless explicitly added to requirements
  • Server infrastructure security hardening and penetration testing
  • Website performance/load testing beyond normal functional use
  • Many users using the system at the same time on different devices (the system is made for only one computer and one user at a time)
  • HTTPS/TLS security between the browser and the server (the system only runs on the local computer; the computer's own user account and file permissions will protect it instead)
  • Sending password-reset emails, unless an email-sending service is set up (if it is not set up, the reset request will just be saved in the log instead of being emailed)

1.2 Quality Objective

To verify the functionality of the AutoSupply POS and Inventory Management System, the project will focus on testing the inventory, transaction, and reporting modules, to guarantee all these operations can work normally in a real business environment.

2   Test Methodology

2.1 Overview

This section describes the levels of testing, defect handling process, and criteria used to determine whether the AutoSupply POS and Inventory Management System is ready for release.

2.2 Test Levels

For the AutoSupply POS and Inventory Management System, the following levels of testing will be conducted:

  • Unit Testing - individual backend functions (e.g., stock deduction, total computation) tested in isolation
  • Integration Testing - frontend, backend, and database modules combined and tested as a group
  • System Testing - the complete, integrated web application evaluated against the specified requirements
  • Backend/Controller Testing - Laravel controllers and business logic (checkout, inventory CRUD, restock, audit logging) tested via PHPUnit feature tests
  • Smoke Testing - basic sanity checks after each build/deployment
  • Regression Testing - re-testing affected modules after defect fixes or feature changes
  • User Acceptance Testing (UAT) - validation with the adviser and/or end-user representative before final submission
  • Usability Testing - checking if the layout looks good and consistent on desktop and tablet screens, and if common tasks (like recording a sale or adding a product) can be done in just a few steps
  • Performance Testing - checking if pages and the dashboard load in 3 seconds or less under normal use, and if the product, invoice, and audit-trail lists still load fast even with many records, using pagination
  • Security Testing - checking if the password is hashed safely, if user input is checked/cleaned to prevent SQL injection and XSS, if the session ends after being inactive, and if login locks after many wrong tries
  • Reliability & Data Integrity Testing - checking if stock deduction works correctly and never goes negative, if the data connecting users, products, invoices, and sales stay correct, and if money amounts are computed consistently
  • Compatibility Testing - checking if the system works correctly on the latest Chrome, Edge, and Firefox browsers when opened locally (example: http://localhost)

2.3 Bug Triage

Reported defects are logged with steps to reproduce, severity, and module affected. The team reviews and prioritizes defects before assigning them for a fix, following this severity classification: Severity 1 - Critical/Blocking, Severity 2 - Major, Severity 3 - Minor, Severity 4 - Cosmetic.

2.4 Acceptance Criteria

2.4.1 Entry-Exit Criteria

  • Entry Criteria for the start of testing will be a hand-off from the developers.
  • Exit Criteria for the end of testing would be:
    • No open Severity 1 or Severity 2 defects
    • 100% test completion
    • At least 95% test pass rate

2.4.2 Suspension Criteria and Resumption Requirements

If the team members report that 40% or more of the executed test cases failed, testing will be suspended until the development team fixes all the failed cases. Testing resumes once a fixed build is re-deployed to the test environment.

2.5 Test Completion / Sign-off

  • Specifies the criteria that denote a successful completion of a test phase.
  • Mandatory run rate of 100% unless there is a clear, documented reason to waive a test case.
  • Pass rate of 95% is mandatory; achieving the pass rate is required for sign-off.

4.2 Test Environment Updated in v2

For backend testing, the required tool is PHPUnit, run via php artisan test. Test files are organized under tests/Feature and tests/Unit and are to be shared with the team via the group repository for review.

Based on the system design, there are two environment setups: a Development setup that uses a local SQLite database file (no Docker container needed) for quick local development only, and a Quality-Assurance (QA) setup where the Laravel app and a MySQL 8.4 database each run inside their own Docker container, managed using Docker Compose, together with a phpMyAdmin container to view the database directly. All automated PHPUnit tests run against the MySQL QA database (configured via .env.testing), not SQLite. To switch between these two setups, only the environment settings need to change, not the code itself.

The following are required for testing the web-based system, in addition to the test machine's base software:

  • A modern web browser (Chrome, Edge, or Firefox - latest version)
  • MySQL 8.4 running inside Docker (used for the QA/automated test environment)
  • PHP 8.5, Composer, and Node.js/npm (for the Vite-based frontend build)
  • Windows 10/11 or an equivalent OS capable of running the above
  • Docker Desktop (or Docker Engine) and Docker Compose, needed for the Docker-based MySQL QA environment
